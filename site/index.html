How a race works

The agent is a model in a loop with three tools. The rules are checked in code, not left to the model: a move to a page that isn't linked from the current one is refused.

get_links(page)

Read the links on any page. Free: as many as it likes, but every list fills its context.

move_to(page)

Follow a link from the current page. One hop. Reaching the target wins.

give_up(reason)

Stop. Counts as a loss.

Scoring. Success rate decides the ranking. Fewer hops break ties. Cost, tokens and time are shown beside it, not ranked on.

Down the rabbit hole

DeepSeek V4.1 Flash found a route to the target, said so, and then never moved. One real loss, how we found the cause, the fix that looked obvious and wasn't, and the one sentence that did fix it.

1 The loss

Penguin to Bauhaus: the shortest route is 3 hops, through Bird and Germany. DeepSeek looked up Penguin, then Bird, then Germany, its context growing each turn. On turn 4 it wrote:

“Germany directly links Bauhaus. So 3 hops. Need see if 2 possible.”

It had the shortest route in hand. Instead of moving, it went through Penguin's links one by one, asking of each whether it might lead to Bauhaus: “Puffin” no, “Auk” no, “Great auk” no. After 188 pages its reply hit the 2,000-token output limit and was cut off. The run ended at 0 hops: a loss.

Replay this run →

2 Not a one-off

DeepSeek lost 19 of its 75 runs on the model leaderboard. Reading every trace: 16 never made a move, 15 already had a complete route among the lists they'd fetched, and 14 ended at the output limit. It wins most races; it loses a share of them the same way, by searching for a shorter route until it runs out of room.

3 The obvious suspect: context

Every list it looks up stays in the conversation, and DeepSeek's reasoning grew with it. So we tested the standard fix, masking old link lists, on all 25 races. Masking did what it promises: prompts shrank and the context-limit losses disappeared. The output-limit losses didn't. They kept happening in prompts a fraction of the size. Context wasn't the cause (see the strategy board).

4 The real cause: two goals, no order

The prompt named both goals of the game:

“You must reach the target page by following links, in as few hops as possible.”

Both count, but in order: a run that reaches the target beats one that doesn't, however many hops it takes, and hops only decide between runs that both get there. The prompt didn't say which comes first, and DeepSeek put hops first. With a 3-hop route in hand, it spent its whole reply trying to prove no 2-hop route existed, and the 2,000-token limit cut the proof off.

5 The fix

We added the order, and wrote down what we expected it to change before running it once:

“Reaching the target is what counts: fewer hops only break ties between runs that reach it. Once you know a route, take it.”

What we took from it
  1. Read the traces before fixing anything. The score said DeepSeek was weaker; the traces said it found routes and didn't take them.
  2. The obvious fix can be the wrong one. Context growth was real and correlated with the failure, but shrinking it fixed a different failure.
  3. Say which goal comes first. Given two goals and no order, a capable model picks one, and it may not be yours.

Method

What was run, how it's scored, and what we can't control. Every number on this page is computed from the committed trace of a real run; nothing is typed in by hand.

The game, with one twist

The Wikipedia game, played through tools. Unlike the human game, the agent can read any page's links for free; only moves count. That's on purpose: it tests knowing when to stop looking and act, like an agent deciding when it has read enough files. It's also why models here rarely loop.

The races

– hand-picked races, measured rather than guessed. Each race's shortest route is found by searching from both ends, and its target's findability is how many articles link to it. Easy: 2 hops. Medium: 3 hops to a well-linked target. Hard: 4 hops, or 3 to a target fewer than 100 articles link to.

A frozen Wikipedia

Every page an agent reads is saved the first time it's fetched, and every later run reads the saved copy. A page edited mid-sweep can't change the task, and any run can be repeated exactly.

The same conditions for every model

Same races, prompt, tools and limits: – turns, a context of – characters, and – output tokens per reply, reasoning included. The context limit is in characters because tokenizers differ: a token limit would give some models less room for the same text.

Scoring

Success rate decides; fewer hops on wins break ties. Cost, tokens and time are shown, never ranked on. A crash (an API error, a provider outage) says nothing about the agent, so it's left out of the score, shown apart, and the run is tried again.

Three runs of everything

Each model plays each race – times. Ranges come from a bootstrap that resamples races and then runs, because repeats of one race tend to go the same way. p-values come from shuffling each race's runs between two setups. At this size, a gap needs to be about 15 points to tell from chance.

What we can't control

Models are served by third-party providers; each is pinned to one, but a provider can change what it serves. Some prices vary by time of day. Tokens aren't comparable across models. And runs vary: the same DeepSeek setup scored 75%, 77% and 87% on three days.

Receipts

Every run writes a trace: each model call with its reasoning, tokens and cost, and each tool call with its result. Every trace records the model, provider, prompt, context strategy, limits and code commit, and results from different setups are never mixed.
